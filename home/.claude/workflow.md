- [x] **Understand first.** Restate the goal and any user constraint ("config in admin, not code", "upgrade, don't uninstall") in one line, and pick only paths that keep it. Name the repo, path, branch or browser you will touch if it is not obvious. Read only what the task touches. Before writing code, grep for an existing helper, script or branch that already does it, and use it. Ask the user only for decisions that are truly theirs; a question must stand alone and carry your recommended default.
  - A question ("is it possible?", "what do you think?", "why X?") gets an answer only: yes/no first, then at most 3 lines. No edits, restarts or setup until the user says go.
  - "Publish"/"apply" for personal tooling (mod, plugin, hook) means install it for all local sessions; GitHub only when named.
  - If the user can unblock you in one step (start a VM, log in, open an app), say what to do and wait instead of building a workaround.
- [x] **Plan small, verifiable steps.** For multi-step work, list the steps (TaskCreate/todo). Each step ends in something you can check.
- [x] **Do, then prove.** Run the real test, build, or app. "Should work" is not done. For anything the user views (UI, plugin, skill, served page, review site), check the exact copy they get: the installed plugin cache, the running server on the pushed commit, the page in a browser. Never report "done" or "stopped" on code alone. Report failures with the shortest decisive output line.
  - Same error or hook block twice: stop. Read the message, change approach, or tell the user. Never reword a blocked command to slip past a hook or the auto-mode classifier.
  - Anything over ~30s (test suites, screenshots, builds) runs in the background with an ETA.
  - Test proxy, config or credential changes on a copy or alternate port first, never live.
- [x] **QC before done.** Workflow is flexible (inline for small work, `/goal` or pstack for big), but QC is not: after code changes (10+ lines, docs excluded), spawn `reviewer` and `guardrail` in one message, fix confirmed findings, re-run `guardrail` until `VERDICT: PASS`, then report. The Stop hook `hooks/qc-gate.sh` enforces this and blocks finishing until it is done.
- [x] **Consent for outward actions.** `git push`, `gh pr merge|ready`, PR comments and killing processes you did not start need the user's latest message to name that action and target. "Ship it" is not "merge". Before opening a PR or asking for re-review: fetch, rebase so the branch is 0 behind base, and read `git diff --stat origin/<base>` for stray files (gitlinks, worktrees). The PR body lists the commands run and their results.
- [x] **Learn from corrections.** When the user corrects you (the `hooks/correction-reflect.py` hook flags it), open with `Reflect: I did X; should have Y.`, fix it, then sharpen or add one rule here if the lesson is general.
- [x] **Report like a human.** What changed, how it was verified, what was skipped, and any risk, in about 3 lines. No narration.
- [x] Process skills from plugins (superpowers, pstack, postman) are tools, not mandates: use one when the task is multi-step, unclear, or is a bug with an unknown cause. Skip them for questions, single-file changes, and lookups.
